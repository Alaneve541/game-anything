# 构建流程：从一句话到一个可玩切片

## 1. 需求收敛（最多问 3 个问题）

默认值先填好，只在答案会改变架构时才问：

| 项 | 默认 | 何时必须问 |
|---|---|---|
| 平台 | Web（桌面浏览器） | 用户提到手机、Steam、小游戏、主机 |
| 视角 | 2D 俯视或横版 | 用户提到 3D、第一人称 |
| 操作 | 键盘加鼠标 | 用户提到触屏、手柄 |
| 引擎 | 按[引擎路由](engine-routing.md) | 用户点名或已有工程 |
| 美术 | 几何占位加程序化色块 | 用户提供素材或要求特定风格 |
| 规模 | 单局 1–3 分钟，可重开 | 用户要求关卡制、长流程、联机 |

需要问时一次问完，不要逐条追问。

## 2. 一页设计稿（写进 `DESIGN.md`）

```markdown
# <项目名>
一句话：<谁> 在 <处境> 下 <做什么>，因为 <为什么好玩>。
核心循环：<动作> → <即时反馈> → <成长/风险> → 回到动作。
操作：WASD/方向键移动，空格/鼠标左键 <动作>，Esc 暂停。
失败：<条件>；重开：R。
单局时长：<60–180 秒>。
本期不做：<5 条>。
验收：<能启动> + <能玩一局> + <截图> + <状态断言>。
```

设计稿不超过一页。写不出「为什么好玩」，说明还没想清楚，先做灰盒试。

## 3. 范围阶梯

| 阶段 | 产出 | 时间盒 | 通过标准 |
|---|---|---|---|
| L0 纸面 | 一句话、循环、操作、砍单 | 15 分钟 | 能向别人讲清 30 秒玩法 |
| L1 灰盒 | 一个场景、一个机制、能输能赢 | 1–3 小时 | 无美术也能玩一局 |
| L2 垂直切片 | 手感、音效、UI、3 分钟内容 | 0.5–2 天 | 外人不用讲解能上手 |
| L3 内容扩充 | 关卡、敌人、成长、存档 | 按项目 | 有 15–30 分钟可玩内容 |
| L4 发布 | 构建、图标、商店页、崩溃处理 | 1–3 天 | 目标平台安装并启动 |

每个阶段结束都要有可执行构建，不允许「下个阶段才能跑」。

## 4. 垂直切片清单

- [ ] 启动到可操作不超过 3 秒
- [ ] 核心动作有即时反馈（动画、音效、粒子、数字）
- [ ] 有明确的失败与重开
- [ ] 有一处难度或节奏变化
- [ ] 暂停、音量、重开可用
- [ ] 窗口缩放不破版
- [ ] 一局能从头到尾，不卡死
- [ ] 有截图与状态断言

## 5. 里程碑写法

```markdown
## M1 灰盒（今天）
做：玩家移动、射击、3 种敌人、血量、失败重开。
不做：美术、音效、存档、菜单。
验收：`npm run dev` 打开可玩；`state()` 中 score/hp 随操作变化；截图 1 张。
```

里程碑按「可验证行为」写，不按「写完哪些类」写。

## 6. 砍单纪律

每期固定写 5 条「不做」。范围膨胀时按此顺序砍：

1. 剧情与文本量
2. 额外关卡与敌人种类
3. 成长/解锁系统
4. 设置项与无障碍
5. 美术精度与特效

最后才砍核心循环的深度。核心循环不好玩，加内容只会放大问题。

## 7. 试玩脚本（自己或找人）

1. 不讲解，让对方玩 60 秒，观察第一处卡住的地方。
2. 问三个问题：你现在想做什么？哪里不明白？什么时候觉得无聊？
3. 只改「卡住」和「无聊」两处，别顺手加功能。
4. 记录改动前后的完成率或分数分布。

## 8. 常见流程错误

- 先搭框架后想玩法，最后发现不好玩。
- 一上来做联网、账号、成就。
- 同时开三条玩法线，每条都没跑通。
- 用「代码量」衡量进度而不是「可玩分钟数」。
- 试玩时不断解释，掩盖了引导缺失。
